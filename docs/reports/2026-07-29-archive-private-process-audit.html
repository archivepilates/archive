현재 실제 흐름

1

회원 최초 사전설문

새 ARCHIVE IN 설문 화면과 레거시 Google Form·Sheet 수집기가 공존합니다. 새 화면의 API 계약은 현재 단절돼 있습니다.

2

수업 요청 생성

bookings와 회차 데이터를 사용해 강사용 전·후 설문 요청과 알림톡 후보를 만듭니다.

3

강사 수업 전 설문

회원 목적·불편사항, 직전 리포트, 오늘 계획을 확인하고 기록합니다.

4

강사 수업 후 설문

핵심 변화, 다음 방향, 홈워크, 사진·영상을 저장합니다.

5

리포트 생성·수정

Gemini가 초안을 만들고, 강사는 발송 전 문장을 수정하거나 재생성합니다.

6

승인·알림톡 발송

승인 후 큐가 전송하지만, 처리 중 수정과 승인 리비전이 원자적으로 묶이지 않습니다.

7

상태·차트 반영

Firestore가 원천이라고 규정했지만 Notion이 표시와 승인 게이트를 함께 담당하는 코드가 남아 있습니다.

8

운영 확인

ARCHIVE CORE에서 단계를 보지만 오래된 미완료 건과 테스트 데이터가 운영 판단을 흐립니다.

주요 문제와 개선 판단

P0

새 회원 최초 사전설문은 현재 제출 흐름이 연결되지 않습니다

화면은 GET 기반 요청 조회와 일반 POST 제출을 기대하지만, 연결된 함수는 Google Sheet webhook 전용입니다. GET은 405이고 POST는 브라우저가 가질 수 없는 secret·sheet 정보를 요구합니다. 알림톡 후보도 설문 ID와 토큰이 없어 발송 적격성에서 막힙니다.

라이브: 설문 화면 200, 초기화 API 405 · Firestore 설문 응답 최신 기록은 2026.06.10

개선: privateSurveyRequests에서 요청·토큰·짧은 링크를 먼저 만들고, 동일 API가 조회·검증·제출·중복 방지를 모두 담당하도록 통합합니다.
P0

승인한 리포트와 실제 발송되는 리포트가 달라질 수 있습니다

큐가 후보를 processing으로 선점한 뒤 강사가 수정하면 후보는 skipped 처리되지만, 이미 실행 중인 워커는 메모리에 가진 이전 후보로 발송을 계속할 수 있습니다. 링크는 현재 record를 동적으로 렌더링하므로 승인하지 않은 최신 문장이 노출될 여지도 있습니다.

개선: reportRevision과 approvedRevision을 분리하고, 발송 후보에는 승인 시점의 불변 문장·미디어 스냅샷을 저장합니다. SOLAPI 호출 직전 트랜잭션으로 리비전과 상태를 다시 확인하며 processing부터 수정·미디어 추가를 서버에서 잠급니다.
P1

회차 Ledger가 단일 예약 원천 전환을 완전히 따라오지 못했습니다

현재 코드 기준 프라이빗 회차 가능 예약은 4,408건인데 Ledger는 3,162건입니다. 차이 1,252건 중 1,194건은 과거 usage_booking_ fallback이고 실제 예약 누락은 58건입니다. 요청 28건·기록 29건은 재계산 회차와 다릅니다.

중요: 1,252건을 전부 백필하면 과거 fallback을 다시 원천으로 승격시키므로 더 위험합니다.

개선: 실제 예약 58건만 먼저 분리 검증하고, fallback은 historicalRoundSeed로 격리합니다. 회차 불일치 문서는 발송 전 검증 게이트에 둡니다.
P1

예약 날짜가 바뀌면 설문·미디어·차트 승계가 끊길 수 있습니다

같은 날 시간 변경은 보정되지만 다른 날짜로 옮긴 수업은 기존 request/record를 재사용하지 못합니다. 취소된 문서에 답변과 미디어가 남고 새 수업에는 새 요청이 생길 수 있습니다.

개선: 예약 ID와 날짜에서 독립된 privateSessionOccurrenceId를 두고 rescheduledFrom, supersededBy 관계로 변경 이력을 명시합니다.
P1

Notion이 표시용이면서 발송 제어용인 이중 역할을 합니다

운영규칙은 Firestore 원천·Notion 표시 전용으로 정리됐지만, 실제 코드는 Notion DB의 발송=true와 발송상태=대기를 읽어 후보를 생성합니다. 삭제된 DB를 조회하는 예약 작업도 최근 로그에서 6회 실패했습니다.

개선: 승인·발송은 ARCHIVE CORE와 Firestore에서만 수행하고, Notion webhook과 예약 발송 작업은 제거합니다. Notion 동기화 실패는 리포트 발송을 막지 않는 별도 투영 큐로 둡니다.
P1

“차트 완료”가 “회원 전달 완료”로 읽히기 쉽습니다

완료 요청 26건 중 회원 리포트 미발송은 20건이고, 운영 문서는 19건입니다. 과거 수업인데 닫히지 않은 요청도 pending 139건, pre_submitted 21건, post_submitted 32건입니다.

개선: 제목 하나로 여러 의미를 합치지 말고 아래의 단일 생명주기를 그대로 보여줍니다.
P2

정기 점검이 페이지 존재 여부를 실제 기능 정상으로 오인합니다

현재 smoke는 페이지 200과 코드 문자열을 주로 확인합니다. 그래서 설문 API가 405여도 롤백 가드, 데이터 정책, 미디어 설정 검사는 모두 통과했습니다.

개선: 합성 요청을 만든 뒤 GET·POST·중복 제출·취소·날짜 변경·리포트 수정 경합까지 검증하는 행동 단위 테스트를 CI와 배포 후 canary에 연결합니다.
P2

설문 UX와 링크 접근 정책을 함께 다듬어야 합니다

최초 설문에는 여전히 목/어깨가 합쳐진 항목과 상세 입력 없는 “기타”가 남아 있습니다. 일부 textarea는 label 연결이 없고, 태블릿 화면에서 고정 제출 버튼이 마지막 문항을 가립니다. 리포트와 설문 파일은 링크를 아는 사람이 볼 수 있는 정책이며 캐시가 1시간 허용됩니다.

개선: 목·어깨 분리, 기타 상세 입력, label·44px 터치 영역, 하단 여백을 보완하고, 회원 리포트는 만료 가능한 capability token과 no-store 정책을 검토합니다.

완료 기준

  • 전용 테스트 요청으로 회원 최초 설문 열기·제출·중복 제출 차단이 검증된다.

이번 점검의 증거 범위

최신 origin/main과 라이브 Hosting release가 동일한 커밋인지 확인했고, 프라이빗 Functions 18개가 모두 ACTIVE임을 확인했습니다. 설문·차트·리포트·CORE 경로를 390·768·1024·1440px에서 읽기 전용으로 점검했으며, GCP Scheduler와 최근 Functions 오류, Firestore의 요청·기록·발송·회차 표본을 조회했습니다.

실제 회원 설문 제출, 강사 설문 저장, 미디어 업로드, Gemini 생성, SOLAPI 발송, Notion·Firestore 쓰기, Firebase 배포는 수행하지 않았습니다. 따라서 이 문서는 “현재 구조와 라이브 계약 감사”이며, 개선 작업 완료 증명은 아닙니다.
