홀딩 안내를 실제 자동화하려면

권장: StudioMate를 원천으로 유지하고, 최초 수강권 연결·기준선 검증 후 명확한 신규 정지만 자동발송합니다. 불명확한 변경만 운영자에게 확인받습니다.

현재 구현의 한계

로컬 소스를 다시 확인했습니다. 현재는 전체 관찰 내용이 바뀔 때마다 식별자 검토를 다시 요구하고, 후보마다 관리자 승인도 필요합니다. 최대 10개 회원·상품만 선택적으로 수집하며, 시간별 수집과 후보 이후 원본 재확인이 분리되어 지연이 늘어날 수 있습니다. 따라서 현재 상태는 안전한 검토형 구현이지 완성된 무인 자동화가 아닙니다.

확인한 화면에 원본 ID가 없다는 사실과, 원본 ID를 어떤 방법으로도 얻을 수 없다는 결론은 다릅니다. 공개 검색에서 StudioMate 홀딩용 공식 API·웹훅 제공 문서는 확인하지 못했습니다. 지원 여부는 미확인이며, 없다고 단정하지 않습니다.

꼭 필요한 것

  1. 발급권을 계속 같은 권리로 인식: 원본 ID를 확보할 수 있으면 사용합니다. 없다면 변하지 않는 발급 증거로 동일 발급권임을 검증한 뒤 내부 UUID를 부여하고 영구 유지합니다. 상품명·행 순서·현재 만료일만으로 구분하지 않습니다. 동일 상품 중복 발급을 구분할 수 없으면 보류합니다.
  2. 최초 기간과 전체 정지 이력: 발급 당시 기간을 1회 검증·저장합니다. 이후 회원 정지의 신규·수정·취소를 추적하고 센터 휴무 연장은 별도로 분류합니다. 과거 건은 계산에만 포함하고 발송하지 않습니다.
  3. 정지 이벤트 식별: 명확한 신규 생성 이력에 고정 UUID를 부여합니다. 수정은 기존 UUID의 개정으로, 취소는 기존 이벤트 취소로 기록합니다. 같은 시각의 중복 이력·이력 누락·관측 사이 취소와 재등록을 구분할 수 없는 경우 자동 판단하지 않습니다.
  4. 운영 검증과 활성화: 실제 수집기 무발송 실행, 신규·수정·취소·동시 실행 검증, SOLAPI 기존 발송 대조, 김기효·배민진 승인 범위의 테스트, 제한 적용 후 배포가 필요합니다. 스텝·테스트 예외는 승인된 단건에만 적용합니다.

권장 흐름

StudioMate에서 정지 처리 → 기존 동기화에서 변경 후보 확인 → 해당 발급권만 상세 수집 → 최초 기간·전체 정지 계산 → 명확한 신규 이벤트 판정 → 후보 생성 → 해당 건 원본 재확인 → 동일 내용이면 기존 큐에서 1회 발송

  • 처음 기준선 설정 때만 과거 이력을 대조하고 기존 건은 발송하지 않습니다.
  • 정상 신규 건에는 매번 수동 승인하지 않고, 검증된 정책에 따라 자동 처리하도록 변경을 제안합니다. 현재 코드에는 아직 적용하지 않았습니다.
  • 발송 전 수정은 같은 이벤트의 후보 내용을 갱신합니다. 발송 후 수정은 자동 재발송하지 않고 운영자 확인으로 남깁니다.
  • Excel이 이미 정지 중인 수강권의 날짜 변경을 누락할 수 있으므로, 정지·예정 정지 추적 목록과 제한된 정기 대조를 병행합니다. 필요한 빈도는 무발송 누락률·수집 시간 측정 후 정합니다.
  • 후보 이후 상세 재확인은 다음 시간별 전체 동기화까지 기다리지 않고 해당 건만 처리하도록 합니다. 공유 브라우저 잠금·작업 큐 대기는 여전히 필요합니다.
  • 중복 방지는 이벤트 고정 키·영구 선점·발송 원장을 유지합니다. 응답 불명확 건은 자동 재시도하지 않습니다.

감지와 발송은 다른 문제

Firestore 변경을 앱에 실시간 표시하는 기능은 제공됩니다. 다만 StudioMate 변경이 우리 Firestore에 들어오기 전에는 이를 감지하지 못합니다. Firestore만 실시간으로 바꾸는 것으로 StudioMate 수집 병목은 해결되지 않습니다. Firebase 공식 실시간 업데이트 문서

웹훅 없이 시간별 동기화를 유지한다면 외부 변경 감지에는 통상 다음 동기화까지 대기할 수 있습니다. 그 뒤 상세 조회와 큐 대기가 추가됩니다. 즉시 안내가 필요하다면 공식 이벤트 지원 확인 또는 CORE 처리 완료 신호가 필요합니다. 아직 실제 지연을 측정하지 않았으므로 시간 단축을 보장하지 않습니다.

추천 실행 순서

  1. 발급권 식별 근거와 모든 페이지의 변경이력 수집 가능 여부를 읽기 전용으로 확인합니다.
  2. 내부 고정 ID·이력 비교로 명확한 변경은 자동 조정하고 모호한 변경만 보류하도록 수정합니다.
  3. 기존 Excel 변경 신호가 모든 정지 변화를 포착하는지 무발송 비교합니다. 부족하면 추적 목록·제한 대조로 보완합니다.
  4. 후보 이후 해당 건 재확인과 정상 건 자동 승인 경로를 만들고, 기존 웰컴 등 다른 발송 흐름과 회귀 검증합니다.
  5. 승인된 테스트·제한 운영 검증 후 배포하고 범위를 확대합니다.

이번 답변에서는 설계 비교만 정리했습니다. 자동 승인 정책, 운영 설정, 회원 데이터, 실제 정지, 알림톡 발송, 배포는 변경하지 않았습니다. 기존 운영규칙도 이번 제안으로 확정 변경하지 않았습니다.
