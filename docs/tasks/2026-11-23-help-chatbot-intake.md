# Archive Help: chat as the primary inquiry intake

- `/` and `/chatbot/` use the same rule-based chatbot, staged employee inquiry, and review. `/inquiry/` is the original staff form fallback; it uses the original schema and UI behavior. The legacy code only contains the previous month-gate update. There is no API route, Firebase, schema/version, CORE routing, or backend change.
- General Q&A remains in the browser. Optional question reuse requires a deliberate click and review; known contact/medical markers are not copied from chat. Contact and consent use structured fields. The name, phone, answers, and details are sent only after the final action to the verified same-origin existing CORE intake endpoint, not to GPT/StudioMate/email. The endpoint still performs authoritative validation/routing.
- Browser session storage saves only the 48-hex opaque pending request key, shared with the old form. The identical payload and key can be retried while the page remains open, and the key is used for lookup only after reload. The UI never declares success without a server-confirmed receipt of the expected shape. An unresolved key prevents a new direct chat submission. Session storage being unavailable fails closed for chat submission; the independent fallback remains available where appropriate.
- No automatic conversion or irreversible reservation/refund/holding actions happen, and no authoritative personal member lookup is implied. Existing direct registered-account lookup takes place in the official member app. No GPT/OpenAI or email integration was added.
- Run `node --test scripts/help-chatbot-*.test.mjs`. Use only a synthetic same-origin backend to test POST, receipt, lost-response recovery, reload lookup and old form fallback; never use actual test submissions on the live endpoint without separately scoped authorization. For hosted validation, sanity-check route/assets and non-submit flows.
