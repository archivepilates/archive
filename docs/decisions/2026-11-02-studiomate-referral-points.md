# StudioMate Myeongji Referral Points

- User confirmed: a new member's qualifying purchase of at least KRW 300,000 earns the referrer 20,000 StudioMate points; one point is worth KRW 1.
- This is the Myeongji studio program, NOT Imweb video-purchase friend-invite credit. Never share eligibility, balances, claims or payout configuration with Imweb.
- Native StudioMate member editing has no dedicated referrer-name/phone fields. CORE Member Registration collects the newcomer and referrer's names/full phones as an operator-declared attribution receipt. Saving it is not membership creation, verified identity, payment or point credit.
- Canonical attribution: `studiomateReferralRequests`, exact studio `5330`, immutable normalized receipt and input hash. Capture is manager/owner-only using existing fresh-session checks. Conflicting attribution is review-only, never silently replaced.
- Canonical native facts: complete fresh member Excel as discovery evidence; existing verified native member/ticket reader for current exact identity, registration order and fully paid purchase. No new StudioMate API endpoints or API-sync mode. Point changes use native browser UI only.
- Reward claim: `studiomateReferralPointClaims`, SHA-256 of studio + native newcomer ID. One lifetime award per newcomer, regardless of changed referrer, ticket, policy or retry. The atomic transaction checks unchanged receipt fields/hash, pending status, claim absence and current configuration.
- Before payout, re-read native member/purchase cancellation/refund/paid state, receipt state/claim ownership, configuration, native point balance and history. Referrer identity must match full phone and name. Keep existing native IDs and balances. Native edits are additive, never balance assignment.
- Only the first eligible fully paid, usable, nonshared regular purchase meeting the threshold is selected. Trial, outdoor/single-use/free/instructor-lesson products and trial/staff/instructor newcomers are excluded. Incomplete facts fail closed. No cumulative purchase inference or arbitrary grant to a mere signup.
- No historical backfill: native newcomer registration must be on/after the explicitly saved rollout cutoff. Existing balances and historical referrals are not re-awarded. Existing positive-balance export is a read-only baseline, not a payout source.
- Native writer follows two dialogs: first `수정` prepares; only second `확인` changes points. It validates the direction, delta, expected post-balance and bound reason. Result requires an independent native read, one exact reason row and reconciled balance/earned/usage counters. Native negative usage is normalized to a magnitude, never a negative balance.
- Any accepted, claimed, dispatching, review or unknown action blocks automatic replay. Cancellation stops pre-dispatch work and is never overwritten by a later claim/review. Post-award refund/correction requires separate operator review; no automatic clawback policy is introduced.
- Existing hourly Excel import owns execution. Fresh complete successful source evidence is required. Notification refresh/manual stale-file import cannot trigger it. No new timer, scheduler, member message or send queue. A persisted document-ID cursor prevents held receipts starving later requests.
- Allowed readers: manager/owner dashboard receives masked contacts and bounded receipt status. Operator worker can read restricted receipts/claims; no member-facing raw collection access is introduced. Native point history is the actual credit proof; CORE status is an audit/read surface, not another wallet.
- Promotion: mocked policy/receipt/claim/source tests, source review, responsive QA, then a limited operator-only native point test and restoration. A separately approved release installs source/config without replaying the test. The first genuine signup-to-payout live event remains a distinct proof, not implied by the operator point test.
