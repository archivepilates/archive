# ARCHIVE PILATES Imweb webhook onboarding boundary

- Purpose: prepare own-site signup and shopping-grade events without granting access from external payloads.
- Canonical permission sources remain current native Imweb member/grade/groups/purchases, approved actual StudioMate attendance, and the immutable first verified grant ledger. Webhook receipt is not eligibility or grant evidence.
- Provisional lane: `workLanes/imweb-app-webhook-onboarding`. Probe shapes, authenticated samples, shadow receipts and OAuth state remain provisional. No downstream action may select recipients or members from this lane.
- Requested native events: END_USER_SIGN_UP, END_USER_SIGN_UP_BULK, END_USER_GRADE_UPDATE. Route and envelope type must agree; site and unit must match. The observed provider example site is accepted only for exact synthetic test fixtures and stored separately.
- Authentication: official portal test sends Authorization equal to the portal's existing authentication information, without a Bearer prefix. Verified by a keyed digest comparison without logging/storing the raw value. Do not extrapolate this observation into an undocumented retry, delivery-order or HMAC contract.
- Delivery identity: event type, provider event time, site, unit and normalized content. Persist a deduplicated receipt transactionally before acknowledgement. Receipt identity never restarts a 40-day window or authorizes an entitlement mutation.
- Allowed readers: existing manager-only workLanes rules; client writes denied. Treat real member UIDs as personal data, not anonymous hashes. Do not put tokens, secrets or unfiltered bodies into reports or receipts.
- Initial execution mode: shadow only. No member mutation, message, order admission, StudioMate/Contacts write, worker-frequency change or automatic source promotion. Existing reconciliation/expiry safeguards remain active.
- OAuth plan: approved own-app credentials in Secret Manager; tokens encrypted with AES-256-GCM before provisional Firestore storage. State/cookie binding, short operator-enabled window, one-use exchange intent and no blind retry after uncertain exchange. OAuth token receipt is not provider review approval or native integration completion.
- Promotion still requires documented canonical source/target collections, worker ownership, matching identity, duplicate rules, allowed readers, forbidden writes, dry-run source-vs-worker comparison and authorized/unauthorized ordinary-member checks. Do not route Imweb hints into the StudioMate-specific adminSyncRequests notification branch.
- Verification: protocol fixtures, event policy fixtures, privacy tests, central/codebase builds, exact-function deploy, actual portal sample sends, stored receipt reconciliation and negative authentication checks. Actual live delivery requires native app approval plus connected-site completion and remains a separate gate.
